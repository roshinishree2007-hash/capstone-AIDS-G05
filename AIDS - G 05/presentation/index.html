Phase 1 • Define

Problem Statement & Research Context

High-performance compute clusters (NVIDIA RTX 4090, A100, H100) are scarce academic resources required for training compute-heavy deep learning models.

Current Lab Dilemma

  • Severe Resource Bottlenecks: Students compete ad-hoc for 20 high-end workstations without a queue.
  • Frequent Overlaps & Double Bookings: Manual logbooks cause students to clash over the same machine.
  • Zero Availability Transparency: Students arrive at the lab only to find all GPUs occupied by overnight training runs.
  • Unfair Usage Monopolies: Single users hoard GPUs for days, preventing others from completing coursework.

Engineered Solution

  • Real-Time Availability Grid: Live visual status of all 20 GPU workstations (Available, Reserved, In-Use, Maintenance).
  • Strict Fair-Share Governance: Maximum 2-hour slots with 1 active reservation per student per day policy.
  • Atomic Conflict Detection: Microsecond JPQL interval overlap validation rejects concurrent bookings.
  • Lab Assistant Verification Desk: Controlled check-in and GPU release lifecycle workflows.

Phase 2 • Data Tier

Relational Schema & 20 Workstation Fleet

Normalized 3NF relational data model enforcing referential integrity and zero data anomalies.

students

Stores student profiles and contact info.

  • id (BIGINT, PK, Auto-Inc)
  • roll_number (VARCHAR 30, UNIQUE)
  • full_name (VARCHAR 100)
  • email (VARCHAR 100, UNIQUE)
  • department (VARCHAR 50)
  • created_at (TIMESTAMP)

workstations

20 seeded GPU workstations with full hardware specs.

  • id (BIGINT, PK, Auto-Inc)
  • workstation_code (VARCHAR 20, UNIQUE)
  • gpu_model (VARCHAR 80)
  • vram_gb (INT) & RAM (INT)
  • status (AVAILABLE | RESERVED | ...)
  • lab_location (VARCHAR 80)

lab_bookings

Time-slot reservations with lifecycle timestamps.

  • id (BIGINT, PK, Auto-Inc)
  • student_id (FK → students.id)
  • workstation_id (FK → workstations.id)
  • booking_date, start_time, end_time
  • status (CONFIRMED | IN_USE | ...)
  • checked_in_at, released_at
Phase 2 • API Contract

REST API Endpoints & Business Rule Engine

Standardized HTTP verb conventions, unified JSON error responses, and deterministic validation.

Core REST Endpoints

  • GET /api/workstations • List all 20 units
  • GET /api/workstations/{id} • Spec details
  • POST /api/bookings • Create reservation
  • GET /api/bookings • List all bookings
  • PUT /api/bookings/{id}/checkin • Assistant check-in
  • PUT /api/bookings/{id}/release • Complete & free GPU
  • DELETE /api/bookings/{id} • Cancel reservation
  • PUT /api/workstations/{id}/status • Maintenance

10 Automated Business Rules

  • Rule 1: Duration capped at maximum 2 hours (120 mins).
  • Rule 2: Max 1 active booking per student per calendar day.
  • Rule 3: Overlap validation: startA < endB AND endA > startB.
  • Rule 4: Unavailable / Maintenance machines cannot be booked.
  • Rule 5: Start time must be strictly before end time.
  • Rule 7 & 8: Controlled Check-In (IN_USE) and Release (COMPLETED → AVAILABLE).
Phase 3 • Implementation

End-to-End System Workflow

From reservation booking to laboratory checkout.

Step 1

Discovery

Student accesses portal, filters 20 workstations by GPU model (e.g. RTX 4090 or A100), and inspects available VRAM/RAM specs.

Step 2

Slot Booking

Student enters roll number, date, time (max 2 hours), and project details. Backend validates conflict rules atomically.

Step 3

Lab Execution

Lab assistant checks in student at desk (marks IN_USE). When training finishes, assistant releases node, freeing GPU for the next student.
